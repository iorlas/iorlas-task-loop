# Glossary

Canonical language for the redesign, new documentation and conversation. Updated 2026-11-13.
Use short, familiar GitHub and Git terms where their meanings fit. Keep a factory term when its meaning differs;
do not invent an extra entity to match GitHub's hierarchy. `task` is the owner's choice instead of `issue`.

These definitions name the target concepts. They do not assert that the existing code, CLI, database or dashboard
already uses them. Literal existing identifiers may be cited when discussing that code. A future rename is a hard
cut, with no aliases or old-format readers; coordinate it with the owning redesign task rather than renaming twice.
Ordinary verbs such as "run the checks" remain ordinary English, not additional execution entities.

## Work and execution

| Term | Meaning | Example / distinction |
|---|---|---|
| task | Work to accomplish, with a description, acceptance criteria and status, tracked in the repository's task tracker. | `tl-123`. The tracker backend may be bd; its product name does not name our work. |
| task tracker | The system storing tasks, requirements, dependencies, questions, answers and task discussion. | Currently Beads, accessed through `bd`. A replaceable backend, not another factory service, ChatGPT component or execution queue. |
| design | The decisions about the intended behavior and structure of the system. | A versioned design document records what was chosen and why. |
| plan | The work proposed to accomplish a task and the conditions for completing it. | Planning produces a usable plan committed at `docs/design/<task-id>/plan.md` on the task branch. It is an input to later attempts, not proof that implementation is complete. |
| step | One bounded operation on a task, with inputs, a result and a completion condition. | Plan, implement, check, review, land. Its code is also the step implementation, not a separate "stage" concept. |
| attempt | One concrete execution try at an operation, such as a step or an individual check. | A repeat (the step-level retry) makes another attempt. A coordinator restart observing the same surviving execution does not. A new execution continuing the same conversation is another attempt. An attempt can fail before launch. |
| session | A conversation with an agent, identified by its harness or chat application. | A step can own several sessions. Each agent execution attempt uses one session, which may serve several attempts. Non-agent checks need none. A process ID is not a session ID. |
| agent | The coding assistant asked to perform work through the agent interface. | An agent can plan or implement. An attempt is its execution record; a session is its conversation. |
| harness | The program that runs an agent and exposes its conversation and tools. | Codex CLI, Claude Code or OpenCode. Launching it is an ordinary action, not another product entity named "harness invocation". |
| ask | A question requiring the owner's answer before the task can proceed. | An unclear change needs a decision. The prompt sent to an agent is input, not an ask. |

At the factory level the execution picture is `task -> step -> attempt`. Inside the checks step, individual checks
may also have attempts. The word has one meaning: a try at the named operation, not a new workflow tier.
The record identifies its operation and context; a step attempt can group the results of its internal check attempts.
An attempt refers to its conversation, usage, logs and artifacts where applicable. Sessions may be reused.
Tool calls are actions inside a conversation; they do not automatically become step attempts.
If the agent implementation launches a harness again internally, that try must remain inspectable rather than
being hidden in an aggregate. How those launch records attach is part of the step-attempt design, not a new public noun.

`run` is reserved for literal existing code/CLI names, ordinary English and GitHub's own workflow runs until the
redesign demonstrates a distinct factory concept that needs it. Do not introduce a second name for an attempt.
`job` and `workflow` retain their GitHub meanings when discussing GitHub Actions; they do not add factory entities.

## Repository and machine

| Term | Meaning | Example / distinction |
|---|---|---|
| repo | A registered local Git repository binding, shared by its linked worktrees. | RepoId resolves canonical Git common-directory identity. Remote host/project is display/delivery information; task identity has its own configured backlog scope. Independent clones have separate local bindings. |
| task branch | The Git reference retaining a task's committed plan and code. | Derived as task/<task-id> within its selected repository. It is not a directory, slot or execution; publishing it does not land the task. A new one is cut at the plan attempt from the person's local `main`'s tip (no fetch; refusal `target` without a local `main`); an existing one (local, else origin's remote-tracking) is resumed as it is, however far `main` moved ([.15 section 17](design/tl-8bh9.4.3.1.15/plan.md)). |
| worktree | A Git checkout linked to a repository, sharing its commits and branches. | Committing in one linked worktree makes the commit available to the others locally; no push is needed for that sharing. |
| workspace | An external or generic name for an execution's working directory; no separate factory entity. | Use worktree for a Git checkout and slot for a reusable managed worktree. Preserve literal names used by external APIs such as GitHub workspace. |
| slot | A managed, reusable worktree reserved for one independently scheduled step attempt at a time. | `s1`. Internal checks may run concurrently. Reservations are local factory state in factory.db; slots are not tracker tasks. Current internal slot tasks are to be retired. |
| factory | The program that schedules tasks and executes their steps. | It has a dashboard and local execution state; it can serve several repos. |
| host | The machine on which an execution happens. | Do not use this product word for a bundle of collaborators. The successor tree has no `*Host` Protocols; the ports are named for what they do (`StatusPorts`, `EvidenceFiles`, ...). |
| profile | The repo's factory settings in `.task-loop.json`, read by `profile.py` from Git at a commit, never the working tree ([tl-8bh9.14.1](design/tl-8bh9.14.1/plan.md)); `tl profile show` prints it. | Strict keys `setup`, `checks` (name, argv, timeout), `required`, `target`, `land` (`manual`, the default: a person lands a passed task; `auto`: each round lands one, read from `main` like `required`). `setup` and the checks are read at the commit under test (the task branch), like a GitHub `push`/`pull_request` workflow; `required` and `target` from the target (`main`), like branch protection (O1, [self-hosting roadmap](design/self-hosting-roadmap.md) section 7). `setup` runs before an implement agent and before each checks block; the implement agent is told to run every command under `checks` itself, offline; the check step then runs them on X (`required` read from the local `main` at the checks admission). |
| setup | The repo's own command(s), named in the profile, that prepare a slot's environment before the agent starts. | Decided 2026-11-11: run by the factory outside the agent's sandbox, with network, from the same ref as the checks. `just install` when the profile names none (this repository: `just bootstrap`). Not a step. Built (S5e-1): the implement attempt's entry runs it after resetting the slot's ignored files and uv folders (`environment.py`); `tl step show` prints its `Setup:` line. |
| agent folders | The three folders an implement agent may write outside its slot (`access.Folders`), beside the slots under `<slots_root>/<repo_id>/`: the scratch `.t/<slot>` (its `TMPDIR`, at most 64 bytes), `.env/<slot>/uv-cache` (`UV_CACHE_DIR`) and `.env/<slot>/uv-tools` (`UV_TOOL_DIR`). Made (or made 0700 again) by the factory before launch, Codex `writable_roots`; the variables and `UV_OFFLINE=1` go to the agent's shell only (`shell_environment_policy.set`), Codex's own process keeps the person's `TMPDIR`. | Built (S5e-2). Not evidence and not the slot. Each must resolve exactly to its place beside the slot (no link). The scratch is emptied before and after setup and after a slot release (only where it belongs); the uv folders by every reset. A plan agent gets none (`writable_roots=[]`). The preflight's `codex sandbox` probe, run in the emptied scratch, checks the shell gets its variables, the folders are writable and `/tmp` is not. |
| config | Machine-level settings: `~/.config/task-loop/config.toml` or `--config FILE` (`machine_config`). | Local paths and account settings. Use `profile` for repo settings. |

A GitHub **runner** executes jobs; a slot is not a runner. A separate clone is not a linked worktree.
One primary checkout per repo per machine remains the recorded direction; cross-machine behavior is
assessed in the repo/store review. A glossary definition does not introduce a new executor service or process model.

## Checks and delivery

| Term | Meaning | Example / distinction |
|---|---|---|
| check | A named automated validation of the work. | A build, lint command or test command. One check may execute many tests. Decided 2026-11-11: the factory runs checks on the host, before any review, with the agent's scrubbed environment and push bar. As built: a named entry of the profile's `checks` at X, run by the check step (block B4). |
| required checks | The checks that must pass before merging. | Use this phrase instead of a separate "gate" concept. A failed required check prevents the merge. |
| pass | A stored successful check result for its recorded code and inputs. | A failure is a result, never a pass. A missing pass means the check can run again. As built (S6b): a check result `passed` in its checks attempt's latest block, for that attempt's X, profile digest and argv digest; never looked up for another X or attempt (no reuse, D9). |
| check key | The inputs that determine whether a stored pass applies. | Code, command, toolchain and relevant environment/inputs; the exact fields belong to the check design. |
| reuse | Use an existing pass when its validity conditions hold. | An optimization, not required recovery state. Do not give it a separate capitalized name such as `Carry`. The verdict `reused` (below) is a different thing: it names a step whose answer changed nothing. |
| push | Transfer Git objects and update refs on a remote. | Publish `task/tl-123` so another PC can fetch it. `publish` (below) names the factory operation that pushes `task/<id>`; the push itself is the transport. This does not merge it into `main`. |
| merge | Integrate a branch into its base branch. | Squash-merge a completed task into `main`. A direct push is still called a push. |
| land | Finish the task's delivery operation: accepted integration, confirmed task completion and any required task synchronization. | Retry unfinished required actions only. Code can be delivered while task completion remains pending. Merge is integration; push is transport. Publishing an unfinished task branch does not land it. As built (tl-8bh9.14.8): `tl step land TASK`, the person's command (and, under the profile's `land: auto`, a round's land phase: the same operation, tl-8bh9.14.136) that squashes the checked X onto origin's `main` as one commit S, validates S when its tree is not X's or `main`'s required names changed, pushes it never forced, and closes the task; a rerun does only what is missing. Run by a round only under `land: auto`: the oldest passed round-taken task, at most one per round; a conflict, a failed re-check on S, a push refused by the remote's policy, a moved branch or a lost claim holds the task with the cause `land:<reason>` (one comment says what a person can do; a held task is never tried again until answered), an unknown is retried next round, `gate_changed` and `no_change` only a person accepts and the task waits. A Ctrl-C stops it as `unavailable:interrupted`, exit 130 (no traceback); the rerun reconciles. It refuses `gate_changed` (exit 1) when S changes what decides a pass (checks, `setup`, required names, configuration files, weakened tests) until the person reruns with `--accept-gate-changes`; rounds leave the last free slot to a waiting land (`slot_for_land`). |
| PR | A pull request proposing changes to a base branch. | Use the short form after "pull request" on first use when the audience needs it. |
| merge queue | PRs waiting to merge after their required checks pass. | Detailed queue policy belongs in [its design](design/merge-queue.md), not in vocabulary definitions. The speculative queue remains held. |

A step may own several actions: land owns merge and push. Naming those actions does not make them separate steps
or independent scheduling units. Define a step by its purpose and completion condition, not by every command it runs.
The checks step owns individual checks such as lint, type checking and tests. Those are checks, not a new tier of
"sub-steps" requiring a "stage" above them. Each check still has its own result, timing, output and retry history.
The check implementation may coordinate those operations; the factory sees the step's completion condition.
Action and operation are ordinary descriptions of behavior, not extra mandatory entities, tables or scheduling levels.
Likewise, tool calls inside a session do not become workflow steps merely because they are observable.

**Status** says where execution is: queued, in progress or completed. **Conclusion** says how a completed execution
ended: success, failure, cancelled, timed out or skipped. Completed does not mean successful. Use **result** for
the returned data, including any conclusion and outputs; avoid a competing product term "outcome" for that conclusion.
This distinction guides future contracts; it does not silently change the values of existing enums or tracker statuses.
Task statuses describe the task's lifecycle; an execution status describes an attempt. A task's **labels** classify
it; **metadata** holds structured task facts; **comments** hold discussion and owner answers. Do not call task labels
Git tags or treat an execution log as task discussion. A parent task can group child tasks without adding another
execution entity.

## Factory vocabulary as built

Added 2026-11-11 from the successor tree (factory.db v14 since H1 of tl-8bh9.14.9, holds since H2, applied by the round since H3; the check step built through S6e; the land, `tl step land`, through L5 of tl-8bh9.14.8). Each word has one meaning across the code, CLI, database and
logs; use it for nothing else. Words for owner-visible output are listed as the code prints them.

| Term | Meaning | Example / distinction |
|---|---|---|
| phase | How far one attempt's launch has got in factory.db: `admitted`, `dispatching`, `registered`, `captured` (`attempt.phase`). | Not a status or a conclusion. `captured` means the result is stored, not that it is verified or published. |
| admission | The one transaction that reserves a free slot, creates the attempt and takes the tracker claim (`admit.py`); a repeat's takeover of the reservation and an advance, both of which claim nothing, are `admit_chain.py`. | The record is the attempt row at phase `admitted`; the operation is what `tl step start` and each round run. A refusal changes nothing, or returns a claim it took. |
| reservation | The factory.db row tying one slot to one attempt (`reservation`, unique on the attempt). | A slot with a reservation is `reserved`. Ended by a slot release. Not a lock and not a tracker claim. |
| slot custody | The per-slot kernel lock (`slot_lock`, label `taskloop-slot`) held around any Git write on a slot by the entry, verify, repeat or release. | Code names: `custody`, `hold`. Held is `locked`; it is never waited for (`slot_busy`). Not a reservation: a reserved slot is not locked while nothing writes. |
| entry process | The process the factory launches for one attempt, `python -m taskloop.attempt_entry` (a checks attempt: `taskloop.check_entry`); its log is `entry.log`. | Distinct from the agent process and from a Git tree entry. Pick this word; do not say "launcher", "runner" or "entry" alone for the process. |
| launch | Start the entry process (`launch.py`). | Distinct from dispatch. |
| relaunch | Start the entry process again for the same attempt, after it was lost or the machine rebooted. | Not a new attempt: same attempt id, same reservation. |
| dispatch | The entry's permit to run the agent: it records the base commit B and the phase becomes `dispatching`. | The agent runs at most once per attempt. |
| claim | The task tracker's claim on a task, taken at admission and renewed (the bd lease, every 100 s) while a step runs. | A slot release keeps it; `--abandon` returns it. Not a reservation. `renew` here means the lease; see `deadline`. Between steps nothing renews it, so a `bd reclaim` on that tracker can revert it once the lease lapses: at the earliest about 5 minutes after a step ends (about 15 with bd's default 10-minute reclaim grace). A round never renews a claim, and retakes one only for a task with no attempt here under `--retake-lapsed` (after a factory.db discard; see round): a task whose claim lapsed is open again while factory.db holds its attempt, and rounds skip it (`attempted`). |
| backlog | The configured task scope inside a tracker, named by `--backlog`. | The same as "backlog scope" above. Not inferred from Git. |
| round | One scheduling pass: settle existing attempts (holding the round-taken tasks that stopped), advance claimed tasks whose step is done, admit approved ready tasks into the slots left free (first, under the profile's `land: auto`, land the oldest passed task the round took), while fewer than `--max-running` (default 3) of the backlog's tasks are in flight (a step starting, running or being settled, or a passed task waiting to be landed, which counts until landed; failed, stuck, unknown, held, landed and abandoned ones do not: the round stops `max_running`, no tracker read), publish verified results, remove `held` from held tasks taken again. | `tl step next` runs one; `tl step rounds` repeats them. A checks attempt is settled like an agent attempt, through the checks launcher (`operations.relaunch_checks`): relaunched while `admitted` and neither its entry nor a command it registered runs (`<task> check relaunch relaunched <id>`; a check or setup command outliving its entry is waited for, `report running`), released once concluded with its entry gone (`<task> check release released|held:<why> <id>`), reported `running` or `stuck:*`, re-run only when a round-taken task's failed `main_moved` (`<task> check advance started <id>`: `main` moved while it ran, no hold, no replan; the third one in a row is held), otherwise never re-run. Holds (H3 of [tl-8bh9.14.9](design/tl-8bh9.14.9/plan.md)): an attempt at `Next: hold` (a round-taken task that failed, is `stuck:*` but `stuck:hung`, or `repeats_exhausted`) and a round-taken advance or publication refused `claim_lost`/`branch_moved` are `hold.hold_task` (`<task> <step> hold held <reason> <id>`, or `hold pending <missing step> <refusal> <id>` written once per refusal); `on_hold` costs no tracker call and no line; an `on_hold` task whose hold removed the round's own label is eligible again when the person adds it back (`hold_status.reingests`; under another label it stays `abandoned`); after publication `hold.clear_holds` removes `held` from tasks taken again (`hold cleared`). A hand-started task (no stored label) is reported, never held. A failed, stuck or held task never stops other advances or ingestion. A ready task carrying `held` that is not a hold of ours the person answered is skipped (`skip paused`): a hand-added `held` pauses admission only, running steps go on. With `--retake-lapsed` (the person's statement that factory.db was discarded; run it once with `tl step next`) the factory's own in-progress task with an expired lease and no attempt here (the claims a discard leaves) is read with the ready set and admitted like a ready one. Without the flag no in-progress task is read, because one factory.db per tracker is assumed only then: another factory.db's claim between steps looks the same. When `no_free_slot` stops a start, each idle slot that is missing, dirty, redirected or on a branch is a `report unusable:<slot>:<why>` line; so is a worktree holding the task's own branch when the start is refused `branch_held` (named, with `git switch --detach` then `tl slot adopt`; no slot content is ever deleted for you). A task deleted from the tracker is a per-task `skip task_missing` (its attempt is cleared by `tl step release --abandon <task>`), never `unavailable:tracker`. The entry retries a captured result's store writes until the attempt's deadline (a locked factory.db is not a hold). Not the dashboard design-round mockups under `docs/design/dashboard/`. |
| move | One thing a round did or saw for one task: one `rounds.log` line. | A round is a list of moves. A task at `Next: land` is one `report land` move, written once while unchanged; under `land: auto` the same round follows it with `land <how>` or the hold's line, under `manual` it waits for the person's `tl step land` (tl-8bh9.14.27, tl-8bh9.14.136). |
| settle | A round's first part: reading each existing attempt's state and doing its next action (verify, release, repeat, publish). | A settled release is the one that follows a collected result. |
| repeat | A new attempt of the same step after the previous one left the slot unsettled, numbered 1 to 3 within a step (`attempt.number`, `repeat_reason`). | The step-level retry. The CLI, the DB and the log say repeat (`repeat`, `repeats_exhausted`); do not say retry for it. A capture retry (`CAPTURE_RETRIES`) is a DB write retried inside one attempt, not a repeat. |
| verdict | The verifier's judgment of one attempt: `verified` or `rejected:<rule>`. | Not a check pass. `reused` is a verified verdict for a step that changed nothing (`effect` `keep`), distinct from the reuse of a stored pass. |
| disposition | The agent's answer word: plan `planned`, implement `implemented`; both `unchanged`, `incomplete`, `needs_owner`. | A property of the answer. Compare effect. |
| step kind | The few values and functions that make a step that step (`steps.StepKind`): its rules, input, answer schema and decoder, artifact rule and repeat feedback. | A code concept, not a registry or plugin: the kinds are a fixed tuple in order (`steps.STEPS` is `(PLAN, IMPLEMENT)`), reached through `steps.kind(step)`; `steps.next_step` is the one sequencing rule, over `steps.ORDER` (`plan`, `implement`, `check`). The check step is no kind (`steps.is_agent` is False): its attempt is a checks attempt. |
| effect | What the factory does with a disposition: `commit`, `keep` or `none` (`execution.effect`). | `planned` and `implemented` are `commit`, `unchanged` is `keep`, `incomplete` and `needs_owner` are `none`. |
| advance | Admitting attempt 1 of the next step once the task's current attempt is done: verified, released settled (claim kept) and published (`admit_chain.admit_next`); also the `Next` word that asks for it. | One tracker read confirms the task is `in_progress` for `taskloop`; no claim and no label check. The new attempt stores the previous X as `attempt.after_commit`, and its entry refuses `branch_moved` when the task branch no longer contains it. Each round advances automatically, before admitting new tasks, oldest settled release first (`rounds.log`: `<task> implement advance started <attempt>`; a refusal about the task is `<task> plan skip <word> <attempt>`); `tl step start` advances by hand. After implement the next step is check: the advance is a checks attempt's admission (`check_admit`; refusals `commit_missing`, `target`, `target_profile`, `no_required` are skips). |
| agent answer | The agent's structured JSON reply, validated by the answer contract. | Not the owner's answer to an `ask`. |
| execution | One agent run inside an attempt, with its stored facts (`execution` table: exit, usage, evidence paths, answer, session state). | Not an attempt: an attempt has at most one execution. |
| agent process | The OS process record of a running agent (`worker_pid`, `worker_pgid`, `worker_start`, `worker_boot` on the attempt). | The column names mirror the `any_agent` library's `Worker` type. Distinct from the entry process that launched it. Its shell commands run outside its process group by design, each in a new session under `bwrap --unshare-pid --as-pid-1 --die-with-parent`: that PID namespace contains them and ends with its parent (Run S finding 6, Linux), so "the agent is gone and its group is empty" is their stop proof too. Setup processes are never in its group. |
| session state | Whether the agent session reference was captured: `complete`, `pending`, `conflict`, `fault` (`execution.session_state`). | Never the Git push. Not a conversation or a harness. |
| capture | Store the run's result, evidence and session state in factory.db (`Attempts.capture`). | Distinct from publish. Entry.log's `publish=` is the capture retry's DB acceptance, a known leftover word. |
| evidence files | The files kept per attempt behind `EvidenceFiles`: stdout, stderr, answer, diagnostic, `entry.log`, each setup run's `setup-<run>.log` and each check's `check-<block>-<name>.log` (both `CappedLog`: 0600, at most 32 MiB, then one `[truncated]` line). | Control state is never read from them. |
| setup run | One run of the profile's `setup` for an implement attempt, before its agent, or for a checks attempt, before each block (`setup_run`, numbered per attempt; the latest is the highest number): its B, the setup digest, the registered command and its conclusion `passed`, `failed`, `timed_out`, `lingering`, `dirty` or `interrupted`. | Not an attempt and not a step. A passed run is reused only by a relaunch of the same, still admitted implement attempt, never by a checks attempt (its slot is first reset hard to X, `environment.prepare_for`); two failed runs refuse `environment:failed`. A command whose stop left survivors is `lingering`. The entry and the slot release never signal it. |
| checks attempt | The check step's attempt (`checks_attempt`, schema v12, written only by `check_store`): numbered per done implement attempt (a re-run adds one); its own slot, D, deadline and entry; `main`'s commit when the required names were read and those names with their argv digests; `admitted`, then `concluded` `passed` or `failed` with a reason; released, maybe abandoned. | Not an `attempt` row and not a step kind. Admitted by `check_admit` (S6d: the advance after a done implement attempt, or a re-run), its entry process is `taskloop.check_entry` (launched over `CheckStore`; its validation flow is `validate`, shared with the land since L2) and its release `check_release` (`ChecksTarget`; the same release serves a land candidate). `tl step show`/`list` show it in place of its implement attempt; `tl step start` advances to it, relaunches it or re-runs it; each round advances to it and relaunches it, and re-runs it only after `main_moved`; `tl step release` releases it first ([tl-8bh9.14.6](design/tl-8bh9.14.6/plan.md) S6a-S6e). Its reason (`Result: collected failed:<reason>`) is `<name>:<conclusion>`, `<name>:not_run`, `setup:<conclusion>`, `profile:<reason>`, `environment:<word>`, `slot:<word>`, `expired[:<name>]`, `main_moved` (a round runs the checks again; held at the third in a row), `commit_missing` or `claim_lost`. While the latest one of an implement attempt is not abandoned, that implement attempt is not current (`factory_schema.SUCCESSOR`): its abandon refuses `changed`. |
| re-run | `tl step start`, or a round for a round-taken task (only after `main_moved`, at most 3 in a row), on a task whose latest checks attempt concluded `failed` and was released: a new checks attempt of the same implement attempt and X (`number` + 1), the earlier one kept (`Earlier: <id> re-run`). | Not a repeat (an agent step's retry) and not an abandon: same claim, no new plan or implement. A round re-runs only a round-taken task's `main_moved`; a third in a row is held. |
| block | One pass over the profile's checks at X within a checks attempt (or at S within a land candidate, the same rows under its key) (`check_result.block`, numbered per checks attempt; the latest is the highest number), after the slot is reset hard to X and set up at X: each check once, in profile order, required or not (`checks.Block`). | Only the latest block's results count. A completed block (every result terminal, or one `lingering` or `dirty` result that stopped it) is never run again; an `interrupted` or missing result repeats it whole. Built (S6b); run by the checks entry (S6c). |
| check result | One check's result in one block (`check_result`, keyed by a checks attempt or, since v13, a land candidate: no foreign key): its argv digest and timeout, its registered command and its conclusion `passed`, `failed`, `timed_out` (its own timeout), `lingering` (a process left after any end), `dirty` (a tracked change or HEAD not at X detached; untracked files are only listed in its log), `undefined` (required, not defined at X; no command) or `interrupted` (stopped by the attempt's deadline, or found gone unfinished). | The "attempt of an individual check" is this row, identified by (checks attempt, block, name). Unfinished, `lingering`, `timed_out` or `interrupted` (`check_store.LIVE_AFTER`) names a command whose group must be proven gone before its slot is reused or released. |
| landed | The land's end: S (or the no-change disposition) delivered to origin's `main` and the task closed in the local tracker; `Next: landed`. | Tracker sync stays the person's (O4): every land answer says "closed locally, not synced (bd dolt push shares it)". The factory never writes the person's checkout: it is updated (`git pull --ff-only`) when they next work there. |
| land candidate | One squash S of a checked X onto origin's `main` at O (`land_candidate`, schema v13, written only by `land_store`): numbered per checks attempt; its validation `same_tree` or `no_change` at insert (no slot), else validated in its own slot to `passed` or `failed`; **pending** while it holds its slot unvalidated, **pushable** when `same_tree` or `passed`, not delivered and not superseded, **superseded** (`moved`, `withdrawn`, `gone`, `abandoned`: history), **delivered** (`pushed` with the remote head, or `no_change`; at most one per checks attempt, index `land_delivered`), then closed (`closed` or `already_closed`). | Built in L1 as schema and store ([tl-8bh9.14.8](design/tl-8bh9.14.8/plan.md) section 25) and in L2 its validation and release machinery (section 26: `validate`, `check_release.CandidateTarget`); L3 builds the land operation that creates, validates and delivers one (`land.land`, with `land_check` and `land_push`, section 27), L4 its close (`land_close`) and S's message (`land_summary`, section 28); L5 the command `tl step land`, its status lines (`Land:`, `Land check:`, `Pushed:`, `Closed:`) and `Next` words (section 29). Its block's results and setup runs use `check_result` and `setup_run` under its own key (`check_store.RESULT_HELD`, the three-way `setup_store.HELD`); no checks-attempt write matches its key. Only a validated candidate is superseded `moved`, `withdrawn` or `gone`; a pending one only `abandoned`, by its abandon release. |
| result sink | Where one block's results and logs go (`checks.ResultSink`): a record bound to its owner and clock; `checks.CheckSink` serves a checks attempt and a land candidate alike (`check_store` and the owner's evidence directory). | The block knows no checks attempt. As built (L2): `CheckSink` serves a land candidate's key unchanged (its writes pass `check_store.RESULT_HELD`); the shared validation flow (`validate`) runs the block for both. |
| park | Return a released slot to a detached HEAD at the attempt's start (D in Commit letters). | The slot release's one Git write (`slot_release.park_slot`, shared by the checks release, which first resets a slot listed detached at X back to exactly X: `environment.reset_to`; for a land candidate, at S). |
| slot release | Ends an attempt's reservation: parks the slot and keeps the claim (`released`); `--abandon` also returns the claim. | A `held:<reason>` word means the slot stays reserved (`held:setup_running`: the latest setup run, unfinished or concluded `lingering`/`timed_out`, still has a process in its command's group; `held:check_running`: an unsettled check result's command still runs). A land candidate's slot is released by the checks release (`check_release.CandidateTarget`, L2): its stop proof includes the land process stored on the candidate; its abandon marks the candidate superseded `abandoned`. Not a distribution `release` (above). |
| task status | What one task is doing, computed once from its stored facts (attempt, release, hold, land and, where known, the tracker's ready read and the slots) by `task_status.task_status`: `running`, `checking`, `settling`, `waiting_for_land`, `landing`, `landed`, `held` (with the hold's reason), `stuck` (with the `stuck:*` or failed word), `finished`, `abandoned`, or `queued` with why not yet (`ready`, `no_free_slot`, `slot_for_land`, `max_running`, `skipped` by a selection rule). | `tl step list` (status column), `tl step show` (`Status:`), the board's card and the drawer, and the round's admission all call it; `Next` stays the word a person acts on. `abandoned` becomes `queued` once the approval label is on the task. Not a step, attempt or phase. |
| abandon | The owner deliberately giving up an attempt with `tl step release --abandon`: the slot is freed, the tracker claim is returned and the task becomes ready again. | Never automatic: a network or agent failure is not an abandon. The next admission is fresh and starts the task at its first step, as after a factory.db discard. Decided 2026-11-13 (tl-8bh9.14.143): a round restarts it while the tracker lists it ready under the round's approval label (`task_status.restartable`: one restart route, no `tl step start` by hand; remove the label to keep it stopped); a hold's abandon is taken again only by the person's answer (`hold_status.reingests`). The unclaim of a closed or deleted task (bd refuses it: "cannot unclaim closed issue", "no issue found matching") is recorded `not_held`, never left `unclaiming` (tl-8bh9.14.9 5.3). |
| delivery rule | How a land decides that its candidate S is on origin's `main` (`land_push`, tl-8bh9.14.8 section 7): `ls_remote` R is S (delivered), R is O (push S, never forced), else the bounded fetch and ancestry (S in the fetched tip: delivered; otherwise superseded `moved` and at most one new candidate per invocation, then `target_moved`). | Recorded only from a `Pushed` answer or from origin's `main` read by `ls_remote` or the bounded fetch (`origin` trusted as the person configured it, no URL comparison: plan section 29.3); never from a log or an unfetched remote-tracking ref. `--withdraw` reads by the same rule and never pushes. |
| land close | After the delivery, the land closes the task in the person's local tracker as `taskloop` (`land_close`, `tracker_client`'s close: one `bd show`, closed is `already_closed`, else `bd close` fenced on the assignee) and records it once on the delivered candidate (`closed` or `already_closed`). | Push first, then close; never claims, unclaims or syncs (`bd dolt push` stays the person's: "closed locally, not synced"). A refused close leaves the task open (`unavailable tracker`, `refused claim_lost` naming the close by hand that works: `bd close <id>` when unassigned, `bd close <id> --force` when another actor holds it, `refused blocked` with bd's words for open children or blockers, `refused task`) and the rerun goes straight to the close; a closed candidate answers `already_landed` with no Git or tracker call. `--withdraw` never closes. |
| land summary | The facts a land reports before it acts (`tl step land TASK --summary`, `land_summary`): the checks attempt for X with each required name's result, the required names at O against the checks', changed argv of required checks, checks added, removed or changed and a changed `setup` at X against O, the gate facts of S against O (changed files with diffstat, configuration files, weakened tests), O and the squash's outcome (same tree, moved, conflict, no change), S's commit message and the diff command. | Facts only, no judgment. It fetches origin's `main` and makes S in Git objects only; no candidate, reservation, push or close. S's message: the tracker title and `(task-id)`, the branch's commit subjects, trailers `Task:`, `Plan:` (when the plan exists at X) and `Checked:`; every outside text one printable line; the person is author and committer, no co-author trailer. |
| publish | Push of `task/<id>` to origin, once an attempt is verified (`publish.py`, table `published_branch`). | Never forced, and it does not land. The other sense, storing a result, is called capture. |
| deadline | The instant by which an attempt must end, set by `--minutes` (`attempt.deadline`). | Renewed to now plus `--minutes` once per reboot, at relaunch. Not the claim lease. |
| stuck | A next-action word meaning only the owner can act: `stuck:expired_admitted`, `stuck:entry_lost`, `stuck:hung`, `stuck:uncollected`, `stuck:conflict`, `stuck:setup_failed` (an admitted attempt 1 whose setup failed twice: rounds report it and never relaunch it), `stuck:checks_refused` (a checks attempt relaunched twice without concluding: each relaunchable refusal its entry counts, and each round's relaunch past the deadline, `late_relaunch`; rounds stop relaunching it, `tl step start` relaunches it by hand). Since H3 of tl-8bh9.14.9 the round holds a round-taken task at any `stuck:*` word but `stuck:hung` instead of only reporting it. | The other `Next` words are `start`, `wait`, `verify`, `repeat`, `repeats_exhausted`, `release` (also a land candidate still holding its slot after its validation), `publish`, `advance`, `done`, `unknown`, `land` (passed checks: no candidate yet, or one pending, pushable, failed, superseded, or delivered and not closed) and `landed` (delivered and closed), `hold` (a round-taken task with a hold cause: due, or recorded and not finished, the round finishes it or a slot or process keeps the claim) and `on_hold` (the hold finished: waiting for the person's answer). Rounds ignore `land` and `landed` and only report a land's `release`. `tl step list --stuck` shows `stuck:*`, `hold` and `unknown`. |
| reserved / locked / held | `reserved`: a slot with a reservation. `locked`: its custody lock is held. `held:<reason>`: a release word (the slot stays reserved). | A slot can be reserved and not locked. Do not use "held" for the other two. A **hold** (below), the `Next` words `hold` and `on_hold` and the tracker label `held` are about a task, not a slot. |
| hold | A task the factory will not advance until a person acts: its round-taken agent attempt's reason recorded in factory.db (`task_hold`, schema v14, written only by `hold_store`), the approval label it was taken under removed and `held` added, the attempt abandoned when the slot allows, and one comment written on the task ([tl-8bh9.14.9](design/tl-8bh9.14.9/plan.md) sections 2 and 5). An abandon plus a tracker note, never a new kind of attempt, step or wait. | As built (H1): the record and its phases (`labels`, the comment lease `commenting_at` of `COMMENT_LEASE` 120 s, `commented_at`, `cleared_at`), the tracker writes (`tracker_client.TrackerHolds`) and the comment (`hold_text`). H2: the operation `hold.hold_task` (record, labels, the abandon through `operations.release_task`, then the comment by the abandon's outcome: claim returned, or kept by a refusal only the person clears) and `hold.clear_holds` (removes `held` once the task is taken again); the cause rule `hold_status.cause` (a failed `done` or `release`, `repeats_exhausted`, every `stuck:*` but `stuck:hung`; the round passes `claim_lost` and `branch_moved`). The round calls both since H3 (section 9 of the plan). While a hold has not recorded its abandon, `tl step start` refuses `held`; a hold whose cause is gone when it acts again (the status read now) is retired (row deleted, `held` removed), never abandoning restarted work. Only a task whose agent attempt has a stored `label` is ever held (`unlabelled` otherwise). |
| label | The tracker label approving autonomous execution, `auto` (`--label`): checked only when a round ingests a new ready task, never on a claimed task's advance. Stored on the attempt (`attempt.label`, v14): written by the admission (`AdmitRequest.label`: the round's `--label` through `StartRequest.label`; None from `tl step start`), copied by an advance and a repeat. A hold removes this stored label, never the round's. | The lock label strings passed to `process_lock` (`taskloop-slot`, `taskloop-rounds`) are lock labels, not task labels. |

Checkout selection has four existing forms: `repo inspect PATH` requires a positional checkout root;
`slot adopt CHECKOUT` requires the person's checkout as a positional; `profile show --checkout PATH` is optional
and defaults to `.`; `step start|next|rounds|land --checkout PATH` requires the flag. Adoption does not accept
`--checkout`. The removed `--max-new` is rejected; use the implemented `--max-running` bound above.

`step rounds --json` is JSON Lines: a normal graceful session writes the existing start and end objects as separate
stdout lines. Early refusals and abrupt end results go to stderr, along with dashboard notices in JSON mode.
Other commands' structured output is a single JSON document. The current [README](../README.md) describes the
shared exit policy: 3 means no reliable result and safe retry (profile unavailable or step unknown); task/repo
inspection failures stay 1 even when the backend is unavailable.

## Conversations, evidence and accounts

| Term | Meaning | Example / distinction |
|---|---|---|
| transcript | The retained record of a conversation, including every message, tool input/result and reasoning output the harness exposes. | A compact dashboard view may collapse content; it must not be mistaken for the retained transcript. |
| log | The chronological record of execution events and diagnostics. | Preparation, a command's output, a retry and the attempt's conclusion. Logs and transcripts remain files behind their readers. |
| dashboard | The read-only local web page showing how the factory performs. | Built, see [dashboard UI](design/dashboard-ui.md); served optionally by `tl step rounds --dash-port PORT` while rounds run. It changes nothing and holds no state of its own. |
| board | The dashboard's one screen: a card per task in a column per step (Ready, Plan, Implement, Checks, Land), plus Held and Landed; optionally in a row per slot. | Not the earlier `Board` screen name of the retired mockups. Columns derive from task state and are never dragged. |
| live tail | The last few lines of the current attempt's agent activity (commands with how long they ran and waited, agent messages, check results), shown in a task's drawer. | A display view of the evidence stream, not a transcript and never control state. |
| artifact | A retained output produced by the work. | A screenshot, PDF, video or report, associated with its producing attempt. A vendor's transcript file is not a screenshot. |
| design artifact | Supporting material deliberately retained with a versioned design. | A selected diagram or screenshot under `docs/design/<task-id>/`; ordinary execution artifacts do not all belong in Git. |
| account | A configured connection with credentials and applicable usage limits. | A subscription or API account. It is not a vendor or a model. |
| vendor | The service supplying models and their usage limits. | OpenAI or Anthropic. One harness may support several vendors. |
| model | The selected model offered by a vendor. | Distinct from the account paying for it and the harness running it. |

Use **live** and **retained** for viewing time, not two competing kinds of conversation. **Normalization** translates
formats into a common representation; it does not authorize truncating the retained content. A native session ref is
opaque to the factory; the agent library provides readable content without exposing its storage format.
Unknown cost is unknown, not zero. A dashboard total is derived from individual attempt records, not a replacement for them.

## Storage ownership

Owner agreed 2026-11-09. This is the target division, not a claim that current source already implements it.

| Owner / location | What belongs there |
|---|---|
| Task tracker | Requirements, task status, dependencies, questions, linked answers and task discussion. An answer that changes requirements must update the task or its linked design, not remain buried in comments. |
| Git | Code, design documents, plans and selected supporting design artifacts. Task design material belongs under `docs/design/<task-id>/`, with the plan at `plan.md`. |
| `factory.db` | Local execution progress, steps/attempts, session references, reservations and pending local operations. Disposable on deliberate discard; intact-DB restart must continue unfinished work. |
| Local evidence storage, behind readers | Transcripts, command output, execution logs and artifacts associated with their attempts. A reference in the database does not move their contents into it. |

The task tracker's maintenance tooling owns protection and recovery of its durable data. The factory does not own
a second task-backup subsystem. Existing task exports remain protected until actual coverage and recovery have
been verified; accepting this responsibility boundary does not prove that current tracker tooling supplies it.
Factory database disposability does not make task records disposable.

Email and other external messages can supply requirements or decisions. Capture the relevant information on the
task or in its linked design; an inbox is not an additional authoritative work store. No email integration is required.

## GitHub references and intentional differences

- [Actions concepts](https://docs.github.com/en/actions/get-started/understand-github-actions): workflows contain jobs,
  jobs contain steps, and runners execute jobs. We borrow familiar words without copying that hierarchy.
- [Run attempts](https://docs.github.com/en/actions/reference/workflows-and-actions/variables): GitHub numbers re-runs
  with `GITHUB_RUN_ATTEMPT`. Our attempt applies to a step, not to a whole GitHub workflow.
- [Check status and conclusion](https://docs.github.com/en/pull-requests/reference/status-checks): lifecycle and terminal
  result are separate. We say check, not "check run", in ordinary product prose.
- [Artifacts](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts): retained outputs
  differ from caches, which can be regenerated.

Task, factory, slot, profile, session, harness, pass and land are intentional short local terms where GitHub's words do not
express this system's meaning. See [the earlier vocabulary discussion](https://github.com/iorlas/iorlas-task-loop/blob/claude/adapter-justifications-73e7b1/docs/design/slot-lifecycle.md)
for its recorded owner choices. The glossary names the concepts; the redesign and TASKNAME tasks own implementation.
