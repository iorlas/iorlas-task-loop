## Top 10 by importance

1. **FORE-OPUS-01** One OpenAI subscription carries every write, and the factory has no admission rule tied to it. Nothing stops a night at 100% of the weekly window, and nothing routes around it.
2. **FORE-OPUS-02** At 22-69 releases a day, every bead longer than half an hour runs through a release. Batch into a release train and put a canary ring in front of the Mac.
3. **FORE-OPUS-03** Disk will run out from caches task-loop does not own (plugin cache, uv, Codex transcripts). The loop's only defence is to stop quietly with exit 0 at 5 GB free.
4. **FORE-OPUS-04** The review epics give their order in prose only: 51 children, 0 deps, all READY. Four parallel loops will start R1-class rewrites before the fixes they depend on.
5. **FORE-OPUS-05** Review sessions, this one included, file beads faster than the factory closes them. Needed: an intake budget, and a quarantine label for review output.
6. **FORE-OPUS-06** Test fixtures write into the live config dir (`cg-*` traces, `/r` runs). The report, reflect digest and dashboard already read them.
7. **FORE-OPUS-07** 356 red release suites in 5 days, with failures concentrated in `*/real/`. Needed: a flake ledger with a quarantine ratchet before the suite reaches 10k tests.
8. **FORE-OPUS-08** The shelf extraction plan creates cross-repo beads (shelf, then tl, then delegate). Nothing models a bead that has to land in three repos in order.
9. **FORE-OPUS-09** `tl selftest` says a new install must pass it before a move. Nothing calls it, and `versions.py` says "Nothing is tested before a move".
10. **FORE-OPUS-10** The per-bead budget is in dollars, and every subscription call reports $0. The real scarce units (tokens, window percent) have no per-bead cap.

## What I think you are NOT thinking about

1. **Your throughput limit is a weekly vendor window, not code.** On 11-01 the devbox alone burned 14 points of the OpenAI week in 11.6 hours. Add the Mac running 4 loops on what is likely the same account **(unverified)** and the week ends on day 3-4. Then every loop polls `busy`/`no_lane`, and since all writes pin `--only-family openai`, nothing routes around it. Review independence is already gone (three closed reflect beads say so). Every reliability fix in ZOOMOUT assumes a lane exists to run on.
2. **The factory is filling the disk with things it is forbidden to delete.** Claude's plugin cache (224 task-loop versions), uv envs and archives, Codex transcripts: the rule "never touch another tool's state" makes them unprunable by tl. The only guard is the loop quietly exiting 0 at 5 GB free. That is an unattended night that does nothing and says nothing.
3. **Your review process is the biggest bead producer.** One session id created 175 tl beads; this round adds 8 lenses × 30 ideas. Inflow beat outflow 61 to 24 on 11-01. Without an intake budget, the factory turns into a machine that implements its own reviews. Lifesim, the product, has 304 open beads waiting behind them.
4. **The order you wrote down is not the order the factory will use.** The zoom-out review sequences 31 items with care. bd sees none of it: every child is READY, the queue sorts by priority then id, and 4 loops run in parallel. R1 (SQLite store) and Z04 (CAS on the JSON stores) can be written at the same time by two Codex workers.
5. **Your tests write into production telemetry.** Fixture traces (`cg-1..3`, `git@x:y/z.git`) and `/r` runs sit in the live config, and they were made in this very session's id window. The M2 scorecard, `tl report` and the reflect digest all read that file. If one fixture leaked, others can leak on the Mac, where the scorecard is computed.
6. **Releasing per bead is the root of the hop class.** FREEZEBUNDLE / HOPSAFE treat the hop as the problem; the volume is the bigger one. 69 versions in a day means 69 new script environments, 69 cache dirs, about 70 red-suite logs, and a near-certain release inside every Mac bead. A 2-hour train removes most of that for free.
7. **Cross-repo work is coming and has no shape.** Extraction to shelf means every package move touches shelf, task-loop and delegate in order. Today's model is one bead, one repo, one land. Z23 (two apps at different shelf versions) is a preview of what each extraction will leave behind.
8. **Human claims never expire.** `release_dead` frees only engine actors. Lifesim has an `in_progress` from 10-17 and 22 beads in a custom `review` status that no code reads. When a second machine joins, those look like work someone else is doing.
9. **Model churn is invisible.** gpt-6-luna became gpt-6.1-sol on 10-31 with no record of why and no before/after numbers. The next vendor model change will look like an engine regression, and you will spend a day on the wrong suspect.

## Where I disagree with the existing documents

- **Z10 (delete agent-runs v1).** It is the only per-worker run index across tools on the devbox (154 rows with lane, model, cwd, transcript), and it is the natural feed for a multi-machine view. Spec it first and delete it only if `status --history` can carry the same fields (FORE-OPUS-32).
- **Z05 / R2 treat the hop as a mechanism problem.** The data says it is a volume problem: 22-69 releases a day. Freeze the bundle if you like, but put a release train first: it is S effort, and it shrinks the whole incident class, the caches and the red-suite pile at once (FORE-OPUS-02).
- **Z06 / ZOOMOUT-REPOOWNER frame multi-machine as "one factory per repo or shared claims".** There is a third option that is cheaper now: split one repo between machines by capability with the existing AFFINITY `needs:` labels (FORE-OPUS-20). The Mac takes Unity beads; the devbox takes the rest.
