## Top 10 by importance

1. **PIPE-OPUS-01**: the KEYERR fix left a livelock. A STALE from the gate run *inside* the land lock loops forever, re-running the full gate under the lock, and nothing bounds it.
2. **PIPE-OPUS-02**: the storm detector and "2 runs with no verdict" do not pause claims. They **exit every loop**, nothing restarts them, and the dashboard says in its own docstring that it cannot show the storm stop.
3. **PIPE-OPUS-03**: CRASHPARK made `ENGINE_CRASH` "transient". It is retried forever with backoff capped at 1 h, never escalates, and is excluded from the storm. A deterministic land bug now loops silently.
4. **PIPE-OPUS-24**: no crash-matrix test exists. That test injects an exception at every step and effect boundary and asserts that an outcome is written, the checkpoint is kept, the bead state is right and the loop stays alive. It would have caught KEYERR, and it catches 03, 04, 05 and 12.
5. **PIPE-OPUS-06**: the root of the KEYERR class is that `Problem` carries both "retry" (STALE) and "fix this" (GATE/CONFLICT/VERIFY). The fix added a branch at each caller; the type should make a STALE fix unrepresentable.
6. **PIPE-OPUS-04**: CRASHPARK's `except Exception` catches `fence.Fenced`. A run that lost its bead then writes a Park and a trace, which breaks "a fenced run writes nothing more".
7. **PIPE-OPUS-05**: CRASHPARK lets `ValueError` through untouched. ValueError is the engine's refusal channel (36+ raise sites in run, land and checks) and the base of `StaleRecord`, `Refused`, `ConfigError`, `JSONDecodeError` and `UnicodeDecodeError`. The most likely late crashes are exactly those the park does not cover.
8. **PIPE-OPUS-09**: every transient pause counts its attempts and never uses the count. `crash`, `worker_failed`, `schema_invalid`, `hung` and `engine_crash` retry for ever.
9. **PIPE-OPUS-10**: push-failure classification matches `rejected` anywhere in the whole push output, hook and judge output included. A protected-branch refusal or a test named `*rejected*` is read as "main moved".
10. **PIPE-OPUS-35**: the hop safe point is placed so that land and close (the riskiest steps) always run on the newest, least-tested code (`run_once.py:184`). That is backwards for reliability.

## What I think you are NOT thinking about

1. **Liveness is not on the board.** All 26 Z-findings and the three RCA roots are about authority, races and trust. None asks "can the factory stop itself and stay stopped?" It can, in at least four ways: storm exit, two no-verdict exits, profile-ahead exit, low-disk exit. Nothing restarts it and nothing tells you (02, 17, 18). An unattended overnight factory's first property is that it is still running at 7am.
2. **Your fixes are written by the same process that wrote the bug, and tested the same way.** KEYERR fixed the outside STALE path and left the inside one (01). CRASHPARK fixed "a crash loses work" (it never lost work: the gate results are cached and the checkpoint and branch stayed). It also introduced a forever-retry (03), a fenced-write path (04) and a ValueError hole (05). The pattern: a one-incident fix with a one-incident test. You need a property test (24) that a fix must pass, not a regression test the fix author writes.
3. **Retry is the default answer to everything, and nothing counts towards "this will never work".** Transient pause attempts are counted and ignored (09). ENGINE_CRASH is transient (03). Unknown delegate values coerce to defaults (19). Push misclassification retries (10). A system with N retry sites and no global "same thing failed K times, stop and ask" will spend tokens and Unity minutes all night on deterministic failures and look green on the board, because every bead shows a future retry time.
4. **The exception hierarchy is the real control-flow graph, and nobody draws it.** `Blocked`, `FixFailed`, `Fenced`, `Exec` (BaseException), `ValueError`-as-refusal, `CheckFault`, `BdFailure`, `StaleRecord` (a ValueError), and bare `Exception` catch-alls in four places. Which handler catches what decides the bead's fate. The C4 component diagram has no arrows for it. Draw the exception diagram once: you will find 04 and 05 in an hour.
5. **The newest code runs the most dangerous step.** The hop safe point before land (35) means every release's first real execution is a push to main and a bd close. Combined with no canary, the first bead after a release is the canary, on the step you can least afford to break.
6. **You cannot see a spin.** Land rows repeat `n=1` (15). The run budget does not tick in the land (14). The lock wait is booked as "waited" (16). A stuck land shows as "waiting for land lock" on every other lane, which reads as normal contention. Ask what signal at 3am separates "busy" from "stuck", and make it a record.
7. **The main checkout is a stale mirror that everyone reads** (31). CLAUDE.md, the docs agents load first, and this review brief all point there. You are reviewing, briefing and diagnosing 0.23.293 while 0.23.301 runs.
8. **Mac and devbox state are separate, so post-mortems are partial.** I found no KeyError and no storm in the devbox `~/.config/task-loop` (empty `loop/*/`, no `exits.jsonl`). The incident lived on the Mac. Nothing collects one machine's incidents onto the other, so cross-machine RCA is guesswork.
