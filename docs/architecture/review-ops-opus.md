## Top 10 by importance

1. **OPS-OPUS-13**: one bad release can end Trust Night. Storm, then every lane exits, the dashboard cannot show why, and nothing restarts the lanes.
2. **OPS-OPUS-15**: no supervisor, no notification, and no remote start, pin or rollback. Any lane exit stays final until someone is at the Mac's shell.
3. **OPS-OPUS-01**: 30 to 69 releases a day, and each one is a production deploy to running factories with no canary and no promotion step.
4. **OPS-OPUS-07**: no host-level concurrency budget. The lane count and resource limits come from a repo's committed file, never from the machine.
5. **OPS-OPUS-06**: per-slot MSBuild and compiler-server ids multiply .NET daemons across slots. This is the first suspect for load 280, ahead of Unity.
6. **OPS-OPUS-03**: the production OS (macOS) is never tested. CI is Ubuntu only, releases run on Linux, and the macOS-only code paths run only against fakes.
7. **OPS-OPUS-02**: CI has been red for 300 runs straight (last green 2026-10-29T23:56Z), and releases ship on a local green.
8. **OPS-OPUS-04**: about 59% of release suite attempts are red, 519 distinct tests failed three or more times, and there is no flake ledger.
9. **OPS-OPUS-09**: no load-aware admission. The loop claims beads whatever the machine's load.
10. **OPS-OPUS-40**: no per-check or per-worker CPU and RSS accounting, so nobody can say what caused load 280.

## What I think you are NOT thinking about

1. **Your release pipeline deploys to production 50 times a day, with no canary, no promotion and an auto-rollback that covers only crashes.**
   The pieces are each fine. Together they make a failure mode no document names: a release at night that makes beads FAULT (not crash)
   is not marked bad (OPS-OPUS-14). It trips the storm detector, every lane exits (OPS-OPUS-13), the dashboard cannot say why, and
   nothing restarts the lanes (OPS-OPUS-15). One bad push ends Trust Night, and you find out in the morning from an "absent loop" row.
2. **Load 280 is probably not "Unity is heavy".** The code isolates .NET per slot on purpose (separate compiler server, separate
   MSBuild node pool, separate NuGet cache per slot and per plain worktree), and lifesim's own Unity limiter defaults to 5 while
   task-loop's says 1. Nobody measures CPU per check or per worker (OPS-OPUS-40), so the guess has never been tested. Measure with
   `ps` during four lanes before buying any fix.
3. **The machine has no say in how hard it is driven.** The lane count, slot count and resource limits all come from a committed
   repo file. host.json is a list of names. The loop never reads the load average. The owner's own interactive Unity session competes
   at the same priority as four lanes (OPS-OPUS-07, -09, -10).
4. **Your test signal has rotted, and you are trusting the green that is left.** CI has been red for 300 runs. About 59% of local release
   suite attempts are red, and hundreds of tests repeat as failures with no flake record. The Linux devbox, the only machine that releases,
   has no Docker, so container tests skip there while the cache says "container suite". macOS, the production OS, is never run. The fast,
   well-designed logic/real/e2e split hides that the two environments that matter most (macOS, Docker) are never exercised.
5. **Load turns into model spend.** Fixed wall budgets (reviewer 10 min, writer idle 25 min) and a max-based "too slow for the writer"
   ratchet read a CPU-starved host as slow workers. The ladder then escalates to costlier rungs and adds write rounds (OPS-OPUS-11, -12).
   A CPU problem is paid for in subscription quota.
6. **Disk grows in four places nobody sweeps.** These are the plugin cache (1.8 GB of task-loop versions on devbox), `loop/<key>/` run
   logs, slot-state (with a NuGet cache per slot), and /tmp test debris (9.4 GB of /tmp on devbox). The only disk guard
   (`min_free_gb` 5) makes lanes exit, and they never come back (OPS-OPUS-38).
7. **The dashboard is the only remote window, and it is the least maintained process.** It is started only by `tl factory start`. It binds
   the tailnet address only if Tailscale answered at that moment, and it keeps running an old install's code (and old engine ports for its
   POST writes) while the engines hop versions all day (OPS-OPUS-17). It also cannot start, pin, roll back or update anything.
8. **Sleep and wall time.** caffeinate `-i` does not cover lid-close or system sleep. Bead budgets are measured with `time.time`
   across reexec (OPS-OPUS-27, low confidence). A sleeping laptop spends the budget and wakes into a burst of overruns.

## Where I disagree with the existing documents

- **rca-zoomout-three.md:19** calls release hops "a design question for the owner, not a defect". At 30-69 releases a day with no promotion
  step, the hop is a running operational defect. Cap hops now (OPS-OPUS-26) and decide R2 later.
- **zoom-out Z05/R2 placed in wave 3.** Wrong order for operations. Z05's own test ("a week of Trust Night logs counting mid-bead hops")
  should run this week, and a one-hop cap plus a Mac standing pin (OPS-OPUS-37) gives most of the value with no redesign.
- **Z21's proposal** ("N behind" on the dashboard, plus `tl factory update`) treats a Mac that does not auto-update as a gap. That is the
  safest property the system has. Make it explicit (promote verb, standing pin), not a warning to clear.
- **Z22 (caffeinate per lane)** fixes a symptom. With a supervisor (OPS-OPUS-15/16), one caffeinate on the supervisor's pid covers
  every lane, top-ups included; per-lane caffeinate is then dead code.
- **Z20 (delegate lock contention)** proposes a measurement that leaves out the host's load. Without it, the test will blame the lock
  for CPU starvation (OPS-OPUS-36).
- **zoom-out section 1, item 6** calls "locks, caffeinate, resource leases are all host-local" a single-machine design flaw. Host-local is
  right for leases and sleep. The flaw is that the host has no budget of its own (OPS-OPUS-07), and that two Unity limiters disagree on
  one host (OPS-OPUS-08).

  `dev/release.py` and `dev/suite.py`) is a better first extraction than most of its list, because delegate has *no* release tool and
  deploys by prose (OPS-OPUS-24). Volume is not the only reason to share code.
- **No document mentions** the storm stop being invisible on the dashboard, though the dashboard's own source says so
