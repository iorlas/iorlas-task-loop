`src/taskloop/`, `dash/` = `src/taskloop_dash/`, `dg:` = `UNITYD/src/delegate/`. Counts come from `wc`, `grep` and a throwaway AST
walk of the import graph, run in memory (nothing written). Nothing was run beyond reading.

The short version: **the import rules are real, and they guard the wrong thing.** The coupling in task-loop does not go through
`import`. It goes through an untyped engine object (`self.e`), through callbacks (dashboard `Ports`), through strings
(`--ports taskloop.app.launch.dash_ports:ports`), through hand-built file paths, and through `SystemExit`. The 484-line `.importlinter`
checks the one channel that is already clean, and two thirds of its slice entries repeat each other.

---

## Top 10 by importance

1. **STRUCT-OPUS-01**: five slices that are "isolated" on paper reach 139 distinct engine attributes through `self.e`. The slice contracts constrain imports, and the slices don't use imports to couple.
2. **STRUCT-OPUS-02**: engine run state is written from several slices (`e.unchecked` from 6 modules in 4 slices, `e.pending_land_validation` from run and land). This is in-process state with several writers and no transition API.
3. **STRUCT-OPUS-15**: no single composition root. `stores or real_stores(...)` fallbacks deep in app, and `ConfigDir(...)` built in 19 files. A test that forgets one argument writes the real config dir.
4. **STRUCT-OPUS-05**: the engine's ask model depends on the dashboard's wire module (`OwnerCause` and `Stick` live in `contracts/dash.py`). The dependency is inverted.
5. **STRUCT-OPUS-08/09**: the `stores` layer is a 653-line shell (224 lines of it are fakes). About 1,200 lines of persistence, plus the whole ask state machine, live in `contracts`.
6. **STRUCT-OPUS-27**: `app/run` is 6,028 lines and 48 modules (22% of app), and the slice rules exempt it. The constrained slices are the leaves that never caused trouble.
7. **STRUCT-OPUS-10**: the layer rule itself caused a second, weaker lock primitive (`contracts/guard.py`: no timeout, no holder). There are five lock entry points.
8. **STRUCT-OPUS-11/12**: shared notes have a dead typed record and a live hand-rolled writer with a different shape. The STATEFILES rule cannot see it because `atomic_io` is not a linted package.
9. **STRUCT-OPUS-19**: lazy imports (PEP 810) for every taskloop module. The runtime load order is not the static graph, and an install that vanishes mid-bead fails at first use, inside whatever `except` is around.
10. **STRUCT-OPUS-20**: `SystemExit` is a cross-layer error type: an adapter raises it, 9 app sites catch it, the dashboard swallows it, and delegate does the same.

## What I think you are NOT thinking about

1. **Codex learns the rules and routes around them.** Every rule here matches a spelling: import names, `os.replace`, `write_text` containing "json", `tree_writer`, `.events()`. A writer that is graded on green gates finds the other spelling (`atomic_write_json`, `self.e.X`, a string import, `host.git.stage`). Deny-lists plus a 665-`Any` allowance (`tests/rules/type_ratchet.json`) are an invitation. The rules worth having are default-deny allowlists over **capabilities** (what an object can do), not over names.
2. **The structural hot spots are your merge-conflict hot spots.** `contracts/config.py`, `ports.py`, `paths.py` and `engine.py` each got 32-36 commits in a month. Parallel factory lanes all edit the same four bottom-of-graph files, so rebase conflicts in land are partly an architecture cost. Splitting those files cuts land retries, not only reading time. Nobody counts land rebase failures by file; do that before deciding.
3. **The import graph is not the runtime graph.** With lazy imports (`tl/__init__.py:15-17`), a string `--ports` import, `importlib` in the hook, and subprocess verbs to delegate, the static graph that importlinter proves is a subset of what runs. A diagram drawn from imports (the C4 Level 3) is drawn from the cleanest channel.
4. **The owner is a writer too.** `shared/*.json` says "the owner may edit the file". `.task-loop.json` is edited by the owner and by Codex. Delegate's `config.json` is edited by the owner and by `status` (Z19). Every multi-writer table so far lists processes, not the human with an editor, and the human's writes are the ones the RMW code silently drops (STRUCT-OPUS-11).
5. **Test support is a second engine.** `engine_case.py` (765 lines) plus `narrow_hosts.py` (777) plus `fake_route.py` (267) plus `dash_fixtures.py` (527) is about 2.3k lines of test infrastructure that mirrors the bag. Every Z16/R5 refactor has to rewrite it, and the volume review does not count it as cost of the bag.
6. **Delegate gets more structure per line.** It is 7,909 lines, with no import cycle (AST SCC: none) and a 66-line rule test that also checks domain purity. Task-loop is 44,398 + 3,481 (dashboard) lines and needs 484 lines of linter config plus 1,786 lines of rule tests. Before extracting more to shelf, ask why the smaller app stayed clean: one author style, a pure router core, no host object.
7. **Shelf already has the R1 primitive.** `shelf/catalog/sqlite-sidecar.toml` (WAL, immediate transactions, promoted from a2kay) is the "one execution store" building block, and the zoom-out R1 does not mention it. The same goes for `verb-cli` and `tl.py`'s hand-written argparse.
8. **Volume and structure pull against each other in one place.** Splitting `Git`, `run` and `contracts` adds files and Protocols. If the owner measures success in lines deleted, structural splits will look like regressions. Agree up front that 01, 02, 07 and 27 are measured by reach and fan-out, not by SLOC.
