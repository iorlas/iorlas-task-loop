## Top 10 by importance

1. **SEC-FABLE-01** The pre-push judge reads the writer's `.task-loop.json` *and runs its `checks[].argv` on the host in-process* when the tree is not green: a writer in any lane, the no-network Codex lane included, gets host code execution (with the owner's ssh agent) on the engine's own push. Z02 calls this "controls the judge" (a bypass); it is RCE.
2. **SEC-FABLE-05** The `claude -p` writer lane has no OS sandbox, full network, the owner's keychain, and a secret regex that does not name `~/.claude/.credentials.json`; the constitution already records that its classifier approves an exfil when the brief asks. On the Mac it is a configured writer.
3. **SEC-FABLE-32** One uid runs owner, engine, judge, dashboard and every worker. The constitution says "a separate user or VM is the real fix" (`dg:docs/dev/constitution.md:27`); nothing in either repo moves toward it. Everything below is a tripwire until this is done.
4. **SEC-FABLE-10 + 13** Any tailnet peer is the owner: no auth, and a POST `/api/note` becomes a "people" comment that the writer must treat "as an accepted requirement" (`DECIDED_RULE`). Prompt injection from the network into every worker, by design.
5. **SEC-FABLE-03** Every repo check inherits `SSH_AUTH_SOCK` and `GIT_SSH_COMMAND` (`childenv.ALLOWED`): a check (repo code by design) can push anywhere as the owner. Only the land command needs the agent.
6. **SEC-FABLE-19/20** `--exec-allow`: task-loop's side silently drops a recipe from engine-only when it is also exec-allowed (the escape wins), while delegate refuses that conflict; and the RCA's accepted option (c) lists `just` recipes, which run the writer's justfile. Both are wrong before anyone calls it.
7. **SEC-FABLE-07** `gh` (and any HTTPS API) bypasses the whole pre-push judge: no guard names it, it authenticates without naming a path, and Z24's env-config push barrier does not touch it.
8. **SEC-FABLE-27/28/29** The OpenCode sandbox lets commands write `~/Library/Caches` and `~/.cache` (the engine's own uv cache), allows unix sockets (docker.sock on OrbStack), and OpenCode itself (outside the sandbox) reads the worktree's project config.
9. **SEC-FABLE-33** The factory releases itself: a bead on `iorlas-task-loop` is written by Codex, reviewed by a model, landed by the engine and shipped by `dev/release.py` to the engine that judges the next bead. No two-person rule, no "privileged bead" notion.
10. **SEC-FABLE-14/15** The reviewer's independence is illusory: it reads the writer's `AGENTS.md`/`CLAUDE.md` as its *system prompt* and is told the writer's `evidence/` folder proves requirements.

## What I think you are NOT thinking about

1. **The judge is also an executor.** Every C4 document treats the pre-push judge as something that *reads evidence*. It also *runs the registry* of whatever tree is being pushed, in-process, as the owner. That turns Z02 from "a writer can skip the gate" into "a writer owns the host", and it is reachable from the Codex lane that the diagrams draw as the safe one. The same shape exists in `land-stack` and in every `tl check` a person runs in a worktree a writer touched.
2. **The reviewer is not independent; it is a second reader of the writer's tree.** Same cwd, the writer's `AGENTS.md` as system prompt, the writer's `evidence/` as proof, and (for the stage checks) tests the writer wrote. "From another model family" is a vendor property, not an independence property. Independence needs: instruction files from the base, evidence rerun by the engine, and the profile/justfile out of the writer's reach.
3. **"No network" has at least five doors.** The link check (200 GETs per review of URLs the writer wrote), the engine's own `git push` of the tree (a secret in a tracked file), a Codex escalation with a one-line justification (the prompt teaches it), bd comments that `bd sync` pushes to GitHub, and the Claude lane which has network outright. Draw them before adding a sixth.
4. **The orchestrating session is the most privileged principal and the least guarded.** It has no sandbox, the owner's keys, `git push`, `release.py`, and one hook rule (pkill). It reads model-written text through `tl wait`, `tl status`, the handoff file after every compaction, and the dashboard's asks. Nobody drew that arrow; everybody hardened the workers.
5. **Tailscale is already an identity provider.** The dashboard went from a token to nothing. `tailscale whois` gives the peer's login for free, per connection, with no UI and no secret. The ZOOMOUT fix (Z08, "spawn `tl` instead of importing") changes who executes a write, not who may ask for one.
6. **Mutable code paths that are not "the plugin".** `~/.cache/uv` / `~/Library/Caches/uv` (the environment every `uv run --script` imports from), `~/.config/task-loop/bin/tl` and `githooks/`, `~/.claude/plugins/cache/`, and uv's cwd config discovery. All writable by at least one lane or by any host check. `MANIFEST.sha256` is checked only by `tl doctor`, which nobody runs before a push.
7. **The engine repo is a privileged target of its own loop.** A bead on `iorlas-task-loop` or `iorlas-delegate`, written by Codex and reviewed by a model, becomes the judge of the next bead after `release.py`, on both machines. There is no notion of a privileged bead, and `release.py` cannot tell a human-reviewed range from a loop-landed one.
8. **Two secret lists, one uid, zero boundaries.** `SECRET_RE` (Claude, Codex) and `SECRETS` (OpenCode) disagree on `~/.claude`; neither names task-loop's or delegate's own state. The constitution already concluded that a regex cannot be the boundary and named the fix. The epic has 31 children and none is "second user".
